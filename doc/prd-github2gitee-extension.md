## 1. 背景与目标

### 1.1 背景

现有 Python / 云主机方案偏重。Gitee 网页已提供：

- **从 GitHub 导入仓库**（首次搬迁，含历史，由 Gitee 服务端拉取）
- **同步更新**（已导入仓上一键强制同步）
- **仓库镜像 Pull**（可配置自动/手动从 GitHub 拉取）

用户需要更轻的入口：在 GitHub 浏览时一键进入上述能力，并管理已备份仓库的后续同步。

### 1.2 目标

开发一款**纯浏览器插件**（Chrome / Edge / Firefox），作为编排层：

1. **新增（场景 B）**：在 GitHub 仓库页一键启动「导入到我的 Gitee」（依托 Gitee 官方导入，而非自建 git mirror）。
2. **同步（场景 A）**：对已导入/已映射仓库，支持手动「立即同步」，并尽量自动同步（依托「同步更新」触发能力或官方 Pull 镜像；必要时轮询后提示用户）。
3. **零自建同步后端**：MVP **不依赖**用户或开发者部署 sync-service / 云主机 git 服务。

### 1.3 非目标（本期不做）

- 不在扩展内执行 `git clone` / `git push --mirror`。
- **不以自建 sync-service 为主路径**（该目录已于 v1.1 从仓库删除）。
- 不用 Contents API 做「逐文件快照拷贝」充当完整同步（除非官方导入不可用时的降级实验，默认不做）。
- 不做 Gitee → GitHub 反向同步。
- 不做组织级批量镜像（仍可用原 Python 工具）。
- 不保证 Git-LFS、超大仓、Gitee 官方超时仓的成功。

### 1.4 能力边界（必须向用户说清）

- 实际搬代码的是 **Gitee**，插件不能突破 Gitee 导入/同步产品与授权限制。
- 「任意他人公开仓静默 API 导入」**不保证**有公开稳定 Open API；MVP 允许「打开 Gitee 导入页并由用户确认」作为主路径。
- 「同步更新」多为**强制覆盖**；须有风险提示。

## 2. 用户与使用场景

### 2.1 目标用户

- 使用 GitHub + Gitee 的个人开发者。
- 希望轻量备份公开项目到 Gitee，并偶尔点同步跟上更新。

### 2.2 场景 B：浏览即新增（导入）

**描述**：在 GitHub 看到感兴趣仓库，一键导入到自己的 Gitee。

**主流程（MVP）**：

1. 用户打开 `github.com/{owner}/{repo}`。
2. 插件显示「导入到 Gitee」。
3. 插件打开（或跳转）Gitee 官方导入流程，并尽量预填 GitHub 仓库地址 / 名称。
4. 用户在 Gitee 已登录状态下确认导入（公开仓按官方流程；私有仓需 GitHub 授权，P1）。
5. 用户回到插件确认「导入完成」或插件通过 Gitee API 检测到目标仓已存在后，写入「已同步列表」。
6. 展示 Gitee 仓库链接与备份提示（勿在 Gitee 直接当主开发仓乱改，若当纯备份）。

**异常**：

- 未登录 Gitee：引导登录后再导入。
- 同名已存在：引导改名、打开已有仓做同步、或取消。
- 导入失败/超时：展示官方页结果，允许重试或仅登记映射。

### 2.3 场景 A：已有仓库同步

**描述**：Gitee 上已有从 GitHub 导入（或已映射）的仓库，需要更新到最新。

**主流程**：

1. 仓库已在插件映射列表中。
2. **手动**：用户点「立即同步」→ 插件优先调用可文档化的触发方式（如 Pull 镜像更新接口）；若不可用，则打开该 Gitee 仓库页并引导点击「同步更新」。
3. **自动（准自动）**：定时比较 GitHub / Gitee 最新 commit；若不一致则尝试自动触发；失败则角标/列表提示「有更新，请同步」。
4. 更新映射状态与时间。

**分支**：

- 已配置 Gitee Pull 镜像且可 API 触发：优先静默触发。
- 仅网页「同步更新」可用：打开页面或指导点击（MVP 可接受）。
- 自有 GitHub 仓 + webhook：P1 增强。

## 4. 非功能需求

| ID | 类别 | 要求 |
|---|---|---|
| N-01 | 轻便性 | **仅安装浏览器插件**即可完成主流程；不要求本机 Python/SSH/自建同步服务 |
| N-02 | 安全 | Token 仅本地存储；日志脱敏 |
| N-03 | 性能 | 插件不做大仓 git 传输；耗时操作在 Gitee 侧 |
| N-04 | 可靠性 | 官方失败时有可理解提示与重试/跳转 |
| N-05 | 兼容 | Chrome / Edge / Firefox |
| N-06 | 合规提示 | 同步更新可能强制覆盖；操作前提示 |
| N-07 | 可维护性 | 业务与 browser API 解耦 |
| N-08 | 依赖透明 | 文档标明依赖 Gitee 官方产品；官方改版时可能需适配深链/触发方式 |

---

## 5. 技术方案约束（需求级）

1. **扩展 = 编排层**：识别仓库、跳转/触发 Gitee 能力、维护映射、轮询与提示。
2. **执行层 = Gitee 官方**：导入、同步更新、Pull 镜像。
3. **禁止**把自建 `git mirror` 服务作为 MVP 必选依赖。
4. **他人公开仓**不假设可写对方 GitHub webhook。
5. **多浏览器** MV3 + 兼容构建。

---

## 6. 验收标准（MVP）

1. 不配置任何自建 sync-service，仅装插件 + 拥有 Gitee 账号，即可从公开 GitHub 仓启动导入流程。
2. 用户完成 Gitee 官方导入后，可在插件中登记映射并看到 Gitee 链接。
3. 对已映射仓，手动「立即同步」能触发 API 同步 **或** 打开带「同步更新」的 Gitee 仓库页（二者至少其一可用且路径清晰）。
4. 轮询发现 GitHub 领先时，列表出现「有更新」状态（自动触发能做则做，不能做必须可提示）。
5. 三端（Chrome / Edge / Firefox）均可完成上述流程。
6. 覆盖风险与「备份用途」提示可见。

## 7. 里程碑建议

| 阶段 | 内容 |
|---|---|
| M1 | 需求/设计切换完成；扩展骨架保留；**sync-service 移出主路径** |
| M2 | Options/Popup/映射；GitHub 页「导入到 Gitee」跳转官方导入；「仅登记映射」 |
| M3 | 手动同步：探测/调用 mirror pull 或跳转「同步更新」；状态机打通 |
| M4 | 轮询检测更新 + 自动触发或提醒；三端回归 |
| M5 | 私有仓、镜像配置引导、体验与文档 |

## 8. 决策与待确认

| 编号 | 结论 |
|---|---|
| D-01 | **已改：主方案 = 纯插件 + Gitee 官方导入/同步更新/镜像**；自建 sync-service 非 MVP |
| D-02 | 轮询默认 20 分钟（可配置 10～60）— 仍有效（用于检测「有更新」） |
| D-03 | 目标仓命名默认同名可改 — 仍有效（导入页/登记映射时） |
| D-04 | MVP 手动加载包 — 仍有效 |
| D-05 | 首次成功后备份提示 — 仍有效 |
| D-06 | MV3 + polyfill 三端 — 仍有效 |
| D-07 | MVP 公开仓 — 仍有效 |

### 仍需实现期验证（Spike）

1. Gitee「从 GitHub 导入」是否存在稳定深链/可预填 `https://github.com/{owner}/{repo}.git` 的入口 URL。
2. 「同步更新」是否存在可复用的公开/半公开 API；与 `remote_mirror/pull` 的关系。
3. 未绑镜像的「导入仓」能否只靠网页 Sync 更新，插件如何稳定唤起。
